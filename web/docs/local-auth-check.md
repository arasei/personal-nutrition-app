# ローカルでの通常ユーザー・ゲスト認可確認

## この確認の範囲

旧Supabaseを開発・検証用DBとして使い、ローカルアプリの既存APIを確認する。
ゲスト開始の正式な画面導線、登録案内、登録への移動、データの保存期間、同時実行・障害時の検証は、この手順だけでは完了しない。

`/dev/auth-check` は `NODE_ENV=development` のときだけ利用できる確認ページ。
`npm run build` 後の `npm run start` やVercelでは404を返す。
認証トークンは画面に出力しない。APIへの認可判断は既存のサーバー処理が行う。
「回答の保存」は実際の書き込みを試みるので、開発用テストデータを使う。

## 準備

1. `.env` と `.env.local` の接続先が旧Supabaseであることを確認する。
2. 旧SupabaseのData APIがOFFであることを確認する。
3. 旧SupabaseのAuthenticationで匿名認証を有効にする。新本番プロジェクトの設定は変更しない。
4. `0_init` とカラム追加マイグレーションが適用済みで、Prisma Client生成・seedが完了していることを確認する。
5. 通常ユーザーA、通常ユーザーB、ゲストGに別々のブラウザープロファイルを用意する。
6. `env -u DATABASE_URL npm run dev` を実行する。
7. 起動ログのLocal URLを開く。以下の例は `http://localhost:3000`。別のポートなら全手順でそのURLを使う。

## 確認ページの使い方

各プロファイルで `/dev/auth-check` を開く。

- 認証状態・ユーザーID・Supabase接続先を確認する。
- 通常ユーザーは「通常ログイン」から既存アカウントでログインする。
- ゲストGは未ログイン状態で「検証用ゲスト認証を開始」を一度押す。
- 「診断開始画面」から既存の診断画面を利用する。
- APIの確認では、対象APIを選択し、必要に応じて診断IDを入力して「APIを確認」を押す。
- 「認証トークンを付けずに送信する」は未認証テストだけでONにする。それ以外はOFFにする。
- HTTPステータスとJSON本文を両方確認する。APIのURLをアドレスバーで直接開く操作では、認証付きテストの代わりにならない。
- ゲストの再読み込み後も同じユーザーIDか確認する。ゲスト再診断の間に認証を終了しない。

## 1. 通常ユーザーA

1. Aで診断を完了し、診断IDをM1として控える。
2. もう一度診断を完了し、診断IDをM2として控える。
3. 履歴一覧に両方が表示され、各履歴詳細・結果を再読み込みして閲覧できることを確認する。
4. M2の結果で比較表示を確認する。APIは `canCompare: true` で、比較対象の栄養素に `hasPrevious: true` があること。差分が0でも比較は正常。
5. 確認ページで、履歴一覧・M1の履歴詳細・M1の結果が200で、本人のデータであることを確認する。
6. さらに診断を開始し、質問1で回答せず止める。この診断IDをM3として控える。
7. M3が未完了でも、M1の結果は引き続き200で閲覧できることを確認する。

## 2. 未認証アクセス

確認ページで「認証トークンを付けずに送信する」をONにする。
履歴一覧、M1の履歴詳細、M1の診断結果が、いずれも401で診断データを含まないことを確認する。
終わったら必ずOFFに戻す。

## 3. 通常ユーザーBからAへのアクセス

1. Bのプロファイルでログインし、確認ページの認証状態が通常ユーザー、ユーザーIDがAと異なることを確認する。
2. Bの履歴一覧は200で、M1・M2が含まれないことを確認する。Bが未診断なら空の一覧でよい。
3. M1の履歴詳細・診断結果は404で、Aの診断データを含まないことを確認する。
4. 以下の「質問・回答の所有者確認」を、BからM3に対して行う。

## 4. ゲストG

1. Gのプロファイルで検証用ゲスト認証を開始する。状態がゲストで、A・Bと異なるユーザーIDであることを確認する。
2. 診断を最後まで完了し、IDをG1として控える。
3. G1の結果画面を再読み込みして閲覧できることを確認する。
4. 確認ページでG1の診断結果は200、`canCompare: false`、`diffRanking: null` であることを確認する。
5. ランキングを確認する。食品・料理などの提案は、提案対象のスコア条件を満たす場合に確認する。
6. 履歴一覧とG1の履歴詳細はいずれも403で、履歴データを含まないことを確認する。
7. M1の診断結果は404で、Aの診断データを含まないことを確認する。
8. 以下の「質問・回答の所有者確認」を、GからM3に対して行う。

## 5. ゲスト再診断

1. G1と同じゲスト認証を維持する。
2. 新しく診断を開始し、質問1で止める。新しいIDをG2として控える。
3. 確認ページでG1の結果を取得し、404で古い結果を含まないことを確認する。画面を開いたままの古い表示だけで判定しない。
4. 未完了のG2の結果も404であることを確認する。
5. G2の診断を最後まで完了する。
6. G2の結果が200で、`canCompare: false`、`diffRanking: null` のままであることを確認する。
7. G1の結果は引き続き404であることを確認する。
8. AからG2の結果を取得し、404であることを確認する。

## 質問・回答の所有者確認

M3はAが所有する未完了のテスト診断。Aが質問1に回答していない状態で行う。

旧SupabaseのSQL Editorで質問1のIDを調べる。

```sql
SELECT id, "order", "questionText"
FROM public."DiagnosisQuestion"
WHERE "order" = 1;
```

BまたはGの確認ページで、トークンなしをOFFにし、診断IDにM3を指定する。

1. 「質問の取得（質問1）」を実行する。期待結果は404。
2. 「回答の保存（質問1・回答値1）」を選び、質問1のIDを入力して実行する。期待結果は404。
3. AのプロファイルでM3の質問画面を再読み込みし、質問1のままであることを確認する。
4. SQL Editorで、M3の回答が作られていないことを確認する。下の文字列を実際のM3のIDへ置き換える。

```sql
SELECT COUNT(*) AS answer_count
FROM public."DiagnosisAnswer"
WHERE "diagnosisId" = 'M3の実際の診断ID';
```

期待値は0。400の場合は、認可拒否を確認できたと扱わず、指定した値と応答を確認する。

## 6. 本人への影響とDB保存

Aのプロファイルで、M1・M2の履歴詳細・結果を再読み込みして再度閲覧できることを確認する。

旧Supabaseで、確認ページに表示されたユーザーIDと診断所有者を照合する。

```sql
SELECT
  u.id AS user_id,
  u."currentGuestDiagnosisId",
  d.id AS diagnosis_id,
  d.status
FROM public."User" AS u
LEFT JOIN public."Diagnosis" AS d ON d."userId" = u.id
ORDER BY u.id, d."createdAt";
```

- A・Bの `currentGuestDiagnosisId` はNULL。
- Gの `currentGuestDiagnosisId` はG2。
- G1は閲覧不可になっても、DB上の行は残る。
- 診断は作成者のユーザーIDに紐づき、別ユーザーへ移っていない。
