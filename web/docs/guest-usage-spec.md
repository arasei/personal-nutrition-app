# ゲスト利用の仕様

## 1. この文書の位置づけ

- ゲスト機能の合意済みの仕様、実装・確認済みの範囲、未決定・未検証の事項を分けて管理する。
- 診断・APIのアクセス制限は、旧Supabaseを開発・検証用としてローカルで確認済み。詳細は [ローカル認可確認手順書の記録](./local-auth-check.md#記録) を参照する。
- 正式なゲスト開始・終了、登録・ログインへの画面導線は、今回のローカル確認の完了範囲に含めない。ゲスト機能全体の完成や本番公開済みを意味しない。
- 今回の仕様書更新では、アプリのコード・Supabase設定・DBスキーマを変更しない。

## 2. 目的と合意済みの方針

登録せずに質問への回答、今回の診断結果、ランキング、食品・料理・生活習慣のヒントまで体験できるようにする。
履歴の蓄積と前回比較は、通常ユーザー向けの継続利用機能とする。

- ゲストはお試し専用とする。
- ゲストの診断結果を通常アカウントへ引き継がない。
- 通常登録後は、新しく診断を開始する。
- ゲストアカウントへのメールアドレスの追加などによる、同一アカウントの通常ユーザー化は今回の対象外とする。
- ゲストの診断データの所有者を、登録先・ログイン先の通常ユーザーへ変更しない。
- 登録率や採用評価への効果は未検証であり、効果が実証された設計とは説明しない。

## 3. ユーザーの状態

| 状態 | 意味 | 基本動作 |
| --- | --- | --- |
| 認証確認中 | 初回の認証状態をまだ確定できていない | 認証が必要な通信・自動遷移・ゲスト作成を開始しない |
| 未ログイン | 有効なセッションがない | ゲスト利用、ログイン、新規登録への入口を表示する |
| ゲスト | お試し用の認証状態がある | 診断と今回の結果を利用できる |
| 通常ユーザー | 通常アカウントで認証されている | 本人の診断・履歴・前回比較を利用できる |

認証確認中はユーザー種別ではなく、判定待ちの状態として別に扱う。
認証情報の取得エラーを、単純に未ログインと扱ってゲストを自動作成しない。

### ゲスト状態の継続（合意済み）

以下は開始・終了処理で採用する仕様であり、全項目が実装・検証済みという意味ではない。

| 操作・状態 | 動作 |
| --- | --- |
| ページを再読み込みする | 有効なゲスト認証を維持し、同じゲストとして利用する |
| タブ・ブラウザーを閉じて再訪問する | 認証情報が残り、有効なら同じゲストとして再開する。閉じる操作だけを利用終了とは扱わない |
| 「ゲスト利用を終了」を押す | ゲスト認証を終了し、画面上の診断情報・入力値・キャッシュをクリアする |
| 新規登録・通常ログインへ進む | ゲスト結果を引き継がない旨を案内し、ゲスト認証の終了成功後に進む |
| 認証情報が失われた、または有効なセッションを回復できない | 古いゲスト結果を復元せず、利用者の明示的な操作で新しいゲスト利用を開始する |

- 有効な認証がある場合、再訪問を理由にゲストユーザーや新しい診断を自動作成しない。
- 再開時も第4節のアクセス制限を維持し、過去の結果すべてを閲覧可能にするものではない。
- 一時的な通信失敗や認証確認エラーだけで、認証情報が失われたと断定しない。エラーを表示して再確認できるようにする。
- ゲスト認証の終了とDB上のデータ削除は別の処理とする。終了しただけでDBデータが削除されるとは案内しない。
- ブラウザーを閉じた後の再訪問、認証情報の消失、終了・登録・ログインへの移動は、正式な画面導線の実装後に検証する。

## 4. 機能とアクセス範囲

| 機能 | 未ログイン | ゲスト | 通常ユーザー |
| --- | --- | --- | --- |
| トップ・使い方の閲覧 | 可 | 可 | 可 |
| ゲスト利用の開始 | 明示的な操作で開始 | 有効なゲスト状態を再利用し、重複作成しない | 通常ユーザーの状態を維持し、勝手に切り替えない |
| 診断開始・質問取得・回答保存 | 認証が必要 | 本人の診断のみ可 | 本人の診断のみ可 |
| 今回の診断結果 | 不可 | 本人の今回の診断が完了した場合のみ可。再診断時の扱いは下記参照 | 本人の完了済み診断のみ可 |
| 今回のランキング・食品・料理・生活習慣のヒント | 個人の結果データの取得は不可 | 可 | 可 |
| 履歴一覧・履歴詳細 | ログイン案内 | 登録案内。履歴データは提供しない | 本人の履歴のみ可 |
| 前回比較 | 不可 | 不可 | 本人の前回データがある場合に提供 |
| 利用終了 | 対象外 | ゲスト利用を終了 | ログアウト |

- トップページにある結果のサンプル表示は、個人の結果データの取得とは区別する。
- ゲストの過去の結果URLへのアクセス範囲は、以下の合意に従う。「今回」を特定する実装方法は本節、同時実行などの残る事項は第9節で管理する。
- 質問数は実際の質問データに従う。説明例のステップ数を固定仕様にしない。

### ゲスト再診断時の結果アクセス（合意済み・通常の操作順でローカル確認済み）

- 新しい診断の作成に成功した時点で、それ以前の本人の診断結果URLを開けなくする。新しい診断の完了は待たない。
- 成功の基準はサーバー側で診断のDB作成が確定したこととする。開始ボタンの押下や、ブラウザーでの成功レスポンス受信そのものを基準にしない。
- 新しい診断が未完了の間も、古い完了済み診断の結果を代わりに提供しない。新しい診断の完了後は、その結果を提供する。
- 新しい診断がDBに作成されなかった場合、この再診断を理由に、それまで閲覧できていた結果を無効にしない。
- DB作成後に通信が切れて成功レスポンスを受信できなかった場合も、サーバー側では作成成功として扱う。
- 結果ページのリンクを隠すだけでなく、結果APIへの直接アクセスでも古い結果データを提供しない。
- この制限はゲストに適用し、通常ユーザーの本人の過去結果へのアクセスは維持する。
- 古い結果を閲覧不可にすることは、DBから診断データを削除することではない。

実装では `User.currentGuestDiagnosisId` に今回のゲスト診断IDを保持する。ゲストの診断作成と参照先の更新を同じトランザクションで行い、結果APIでは、本人が所有する完了済み診断で、かつこの参照先に一致するものだけを返す。

G1完了後にG2を作成すると、G2が未完了でもG1の結果が404となり、G2完了後はG2のみ取得できることをローカルで確認済み。同時実行、DB作成失敗、DB作成後のレスポンス受信失敗は未検証であり、上記方針どおりに動くことを後続で確認する。

## 5. 登録案内の文言

### ゲスト開始前

> 登録せずに、診断と今回の結果をお試しいただけます。
> ゲスト利用中の診断結果は、新規登録後のアカウントには引き継がれません。

ボタン：`ゲストで試す`

### 結果表示後

> これからの食生活の変化を記録しませんか？
>
> アカウントを作成すると、登録後に行った診断の履歴を保存し、前回との変化を確認できます。
>
> ゲスト利用中の診断結果は引き継がれません。登録後に新しく診断を開始してください。

主なボタン：`アカウントを作成する`

この案内を結果ページ内に配置する場合、登録しなくてもそのまま結果を閲覧できる。
別画面・ダイアログにする場合は、ゲスト利用を終了せずに結果へ戻る操作を用意する。

### 履歴へのアクセス時

> 診断履歴はアカウント登録後に利用できます。
> 登録後に行った診断を保存し、過去の結果や前回との変化を確認できます。
> ゲスト利用中の診断結果は引き継がれません。

ボタン：`アカウントを作成する`

### 使用しない表現

- `今回の結果を保存する`：今回のゲスト結果を登録後へ引き継ぐと誤解されるため。
- `この結果を保存しませんか？`：同上。
- `終了するとデータは削除されます`：削除処理と保存期間が未確定のため。
- `無料で登録する`：料金方針の確認なしには使用しない。

## 6. ゲスト終了・通常アカウントへの移動

- ゲストには、通常ユーザーの「ログアウト」と区別できる「ゲスト利用を終了」を表示する。
- 新規登録や既存アカウントでのログインへ進む際は、引き継ぎがないことを案内する。
- ゲストセッションの終了が成功してから、通常の登録・ログイン処理へ進む。
- 終了に失敗した場合はエラーを表示し、登録・ログイン処理へ進まず再操作できるようにする。
- 登録案内の表示だけでは、ゲストセッションを終了しない。
- 登録画面・ログイン画面へ直接アクセスした場合も、ゲスト終了の処理を迂回できないようにする。
- ゲストの入力値・結果・キャッシュを、通常ユーザーの表示に残さない。
- 認証変更・画面離脱後の古い通信結果を反映しない、既存の対策を維持する。

## 7. 認証・権限制御の設計方針

- 認証方式はSupabase匿名認証を採用し、旧Supabaseとローカル専用の確認画面で動作確認済み。正式なゲスト開始の画面導線と本番公開の確認は別途行う。
- ゲスト用の認証を利用し、未認証のまま診断APIを公開する変更は行わない。
- 共通フックで画面表示用の状態を管理し、API側では認証を検証したユーザー情報から権限を判断する。
- クライアントから送られた `isGuest` などの自己申告を権限判定の根拠にしない。
- 診断IDと認証済みユーザーIDによる所有者確認を維持する。
- 履歴リンクを非表示にするだけでなく、履歴一覧API・履歴詳細APIでもゲストのアクセスを拒否する。
- 結果APIでは、ゲストの前回診断取得・比較計算を行わず、比較データも提供しない。
- ゲストの「比較する権限がない」と、通常ユーザーの「前回の診断がない」は別の状態として扱う。
- 既存のランキング・ヒントの表示を壊さないよう、結果APIのレスポンス型と表示側を合わせて設計する。

## 8. データ保存の意味

現在の診断処理は、回答・結果をDBへ保存する構成である。
ゲストの「履歴を提供しない」は「DBに保存しない」という意味ではない。

- 診断の処理に必要な回答・結果は、ゲスト本人に紐づけて保存する。
- 通常ユーザーへデータを移動・統合しない。
- ログアウトやブラウザー側の通信中止を、DBデータの削除・保存取消しとして扱わない。
- 保存期間・削除方法が決まるまで、「一定期間後に自動削除される」とは案内しない。

## 9. 未決定事項と決定するタイミング

| 項目 | 決める内容 | 決定期限 |
| --- | --- | --- |
| 診断開始の同時実行 | `currentGuestDiagnosisId` による特定方法は実装済み。同時に診断開始された場合の優先規則と、利用者に示す結果を決める | 同時実行テストの設計前・公開前 |
| 保存期間と削除 | 匿名認証ユーザー、アプリのUser、診断、回答、スコアをいつ・どの順に削除するか。失敗時の再処理も含む | 公開前 |
| 大量作成への対策 | CAPTCHAやレート制限など、匿名ユーザー作成と診断APIの対策 | 公開前 |

未決定事項を、実装上の都合だけで確定済みの仕様として扱わない。
ゲスト状態の継続方針は第3節で合意済み。未決定事項とは分け、実装後の受け入れ条件として第10節で確認する。
削除処理・データ移行・本番設定変更は、この仕様書を更新する作業には含めない。

## 10. 受け入れ条件と確認状況

### ローカルで確認済みの範囲

以下は実施者の確認結果に基づく。詳細・APIステータス・再確認の経緯は [ローカル認可確認手順書の記録](./local-auth-check.md#記録) に残す。

- ゲストが診断から今回の結果・ランキング・条件に応じたヒントまで利用できる。
- ゲストの履歴一覧・履歴詳細APIが403となり、履歴データを提供しない。
- ゲスト向けの結果APIレスポンスが `canCompare: false`、`diffRanking: null` である。
- 通常の操作順で、新しいゲスト診断が作成されると、未完了でも古い結果APIは404になる。新しい診断が完了すると、その結果を取得できる。
- 認証トークンなしで履歴一覧・詳細・結果APIへアクセスすると401となり、診断データを提供しない。
- B・GからAの未完了診断の質問取得・回答保存が404となり、対象診断の回答件数は0のままである。
- 別ユーザーの結果・履歴詳細を取得できず、通常ユーザーの履歴一覧にも別ユーザーの診断が含まれない。
- 通常ユーザーの診断・履歴・前回比較が動作し、上記の拒否確認後も本人が履歴・結果を閲覧できる。
- ゲストの再読み込み後も同じユーザーIDで利用できる。

### 正式な画面導線の実装後・公開前に確認する範囲

- 認証確認中にゲストを自動作成しない。
- 通常ユーザーを意図せずログアウトさせたり、ゲストへ切り替えたりしない。
- 有効なゲスト認証を再利用し、開始ボタンの操作でゲストユーザーを重複作成しない。
- 第3節の方針どおり、再読み込み・タブやブラウザーを閉じた後の再訪問でも、有効な認証があれば同じゲストとして再開できる。
- 認証情報が失われた場合、古いゲスト結果を復元せず、明示的な操作で新しく開始できる。一時的な認証確認エラーでは自動作成しない。
- 正式な画面導線から診断・結果を利用でき、ゲストの履歴画面では登録案内を表示する。確認済みのAPI制限を維持する。
- 新しい診断のDB作成が失敗した場合、それまで閲覧できていたゲスト結果を引き続き取得できる。
- DB作成成功後にレスポンスを受信できなかった場合も、古いゲスト結果を取得できない。
- 登録案内に、ゲスト結果を引き継がない旨が表示される。
- 「ゲスト利用を終了」で認証を終了し、画面上の診断情報・入力値・キャッシュをクリアする。終了をDBデータの削除とは案内しない。
- ゲスト終了が失敗した場合、通常の登録・ログイン処理へ進まない。
- 登録・ログイン画面への直接アクセスでも、ゲスト終了の処理を迂回できない。
- 通常アカウントでログインした後、ゲストの結果・履歴・入力値が混在しない。
- 正式な画面導線の変更後も、確認済みの通常ユーザー・ゲストの診断とアクセス制限が維持される。
- 画面離脱・別タブログアウト・連打・通信失敗からの復帰が従来どおり動作する。
- 第9節で今後確定する同時実行・削除・大量作成対策を検証する。
- Previewで確認し、本番公開の可否を別途判断する。
